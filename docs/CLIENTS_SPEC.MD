# Справочник клиентов (LOG-044 / LOG-045)

Статус: утверждено с тремя уточнениями (лог замещения по имени, миграция партий по точному имени, подразделение в Excel по названию или UUID). Текст ждёт финального подтверждения. Реализация не начата.

Документ опирается на текущий код и на `docs/PROJECT_VISION.MD`, `DATA_MODEL.MD`, `API_SPECIFICATION.MD`, `FRONTEND_SPEC.MD`, `MVP_ROADMAP.MD`.

Префикс API везде `/api/v1`, как у остальных эндпоинтов.

---

## 1. Цель фичи

Справочник клиентов с привязкой к подразделению (управлению продаж) нужен для трёх вещей:

- единообразия: в запросе клиент выбирается из списка, а не вводится свободным текстом;
- аналитики неснижаемого запаса (НЗ) по подразделениям;
- топ-10 клиентов по объёму НЗ.

Внешний ключ клиента — `client_code` (ID КССС). По нему идёт интеграция с ERP и разбор Excel. ИНН остаётся реквизитом и ключом уникальности не является.

Сейчас клиента нет как сущности. Имя хранится строкой `client_name`. Подразделения — общий справочник компании (в сидах: «Коммерческий отдел», «Планирование производства», «Экономический отдел», «Логистика»). Отдельного типа «управление продаж» нет: аналитика группирует то, что лежит в `departments`.

## 2. Модель данных

### 2.1. Таблица `clients`

Следующая ревизия Alembic после `0024_mv_normative_daily`: `0025_clients`.

```sql
CREATE TABLE clients (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    client_code BIGINT NOT NULL,
    inn VARCHAR(12) NOT NULL,
    name TEXT NOT NULL,
    kpp VARCHAR(9),
    department_id UUID REFERENCES departments(id),
    is_active BOOLEAN NOT NULL DEFAULT true,
    is_system BOOLEAN NOT NULL DEFAULT false,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    deleted_at TIMESTAMP WITH TIME ZONE,
    CONSTRAINT ck_clients_client_code CHECK (
        client_code >= 1 AND client_code <= 9999999999
    )
);

CREATE UNIQUE INDEX uq_clients_client_code
    ON clients (client_code)
    WHERE deleted_at IS NULL;

CREATE INDEX idx_clients_inn
    ON clients (inn)
    WHERE deleted_at IS NULL;

CREATE INDEX idx_clients_department_id ON clients (department_id);
CREATE INDEX idx_clients_is_active ON clients (is_active) WHERE is_active = true;

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_clients_name_trgm
    ON clients USING gin (name gin_trgm_ops);
```

Колоночный `UNIQUE` на `client_code` не ставится. Уникальность только среди неудалённых: после soft delete тот же КССС можно завести снова. Ограничение `CHECK` не даёт числу длиннее 10 знаков. `BIGINT` сам по себе вмещает больше.

`pg_trgm` в проекте сейчас не включён. Поиск по названию в остальном коде — `ILIKE`. Индекс обязателен в миграции; до большого объёма список может искать через `ILIKE`.

ИНН не уникален. Один ИНН с разными КПП допустим: карточки различаются кодом КССС.

`is_system` помечает служебную запись «Общий клиент». Её нельзя удалить и нельзя изменить (`client_code`, ИНН, наименование, КПП, подразделение, активность).

Код `9999999999` зарезервирован за служебной записью. Обычный клиент с этим кодом не создаётся.

### 2.2. Поля

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| id | UUID | да | PK |
| client_code | BIGINT | да | ID клиента в КССС, 1…9999999999. Уникален среди неудалённых. Основной ключ ERP и Excel |
| inn | VARCHAR(12) | да | ИНН: 10 или 12 цифр. Контрольная сумма не проверяется |
| name | TEXT | да | Наименование, 1…500 символов |
| kpp | VARCHAR(9) | нет | КПП: 9 цифр, если задан |
| department_id | UUID | нет | Подразделение → `departments.id`. Пустое значение — группа «Без управления» |
| is_active | BOOLEAN | да | Доступен в автокомплите. По умолчанию true |
| is_system | BOOLEAN | да | Служебная запись. По умолчанию false |
| created_at | TIMESTAMPTZ | да | |
| updated_at | TIMESTAMPTZ | да | Обновляется в сервисе при записи |
| deleted_at | TIMESTAMPTZ | нет | Soft delete |

### 2.3. Связи

- `clients.department_id` → `departments.id`, многие к одному, `ON DELETE RESTRICT`. Подразделение с неудалёнными клиентами не удаляется (сейчас удаление блокируют только пользователи; правило расширяется).
- `requests.client_id` → `clients.id`, `NOT NULL`, `ON DELETE RESTRICT`.
- `normatives.client_id` → `clients.id`, `NOT NULL`, `ON DELETE RESTRICT`.
- `production_requests.client_id` → `clients.id`, `NOT NULL`, `ON DELETE RESTRICT`.
- `production_request_items.client_id` → `clients.id`, `NOT NULL`, `ON DELETE RESTRICT`.

Индексы:

```sql
CREATE INDEX idx_requests_client_id ON requests (client_id);
CREATE INDEX idx_normatives_client_id ON normatives (client_id);
CREATE INDEX idx_production_requests_client_id ON production_requests (client_id);
CREATE INDEX idx_production_request_items_client_id ON production_request_items (client_id);
```

`idx_requests_client_name` не удаляется: старые фильтры ищут по тексту.

У подразделений нет отдельного числового кода, только UUID и название. В Excel клиентов колонка «ID подразделения» принимает и то и другое: UUID `departments.id` либо точное название (п. 3.6).

### 2.4. `client_name` после миграции

`client_name` остаётся физическим полем там, где он есть сейчас (`requests`, `normatives`, `production_requests`, `production_request_items`). Это снимок наименования на момент записи.

Новая запись пишет оба поля: `client_id` из справочника и `client_name = clients.name`. Переименование клиента историю не переписывает. Аналитика дашборда читает актуальное `clients.name` через `client_id`.

Ответы API, которые уже отдают `client_name`, продолжают отдавать снимок. Рядом добавляется `client_id`.

### 2.5. Служебный клиент и миграция

```sql
INSERT INTO clients (id, client_code, inn, name, is_system, is_active)
VALUES (
    '00000000-0000-4000-8000-000000000001',
    9999999999,
    '0000000000',
    'Общий клиент',
    true,
    true
);
```

`department_id` остаётся `NULL`, `kpp` пустой.

Порядок миграции:

1. Создать `clients`, индексы, расширение `pg_trgm`.
2. Вставить служебного клиента с фиксированным id.
3. Добавить `client_id` (сначала nullable) в `requests`, `normatives`, `production_requests`, `production_request_items`.
4. Проставить `client_id`:
   - `requests` и `normatives`, включая мягко удалённые, — всегда служебный клиент;
   - `production_requests` и `production_request_items` — по имени, см. п. 2.5.1.
5. Выставить `NOT NULL` и внешние ключи.
6. Тексты `client_name` не менять. Отдельные карточки из уникальных имён не создавать.

### 2.5.1. Миграция партий по имени

Для каждой строки `production_requests` и `production_request_items` отдельно:

| `client_name` | `client_id` |
|---------------|-------------|
| Пустой или одни пробелы | Служебный клиент |
| После снятия пробелов точно совпадает с `clients.name` одной неудалённой карточки, без учёта регистра | Эта карточка |
| Совпадений нет или их несколько | Служебный клиент |

Совпадение строгое: `lower(btrim(client_name)) = lower(btrim(clients.name))`, не поиск по подстроке. Несколько карточек с одним именем не выбираются наугад.

В этой же миграции до шага 4 в справочнике есть только служебный клиент. Имя из истории поэтому сопоставится с карточкой, только если оно равно «Общий клиент» либо если карточки уже загружены в `clients` до этого UPDATE. Остальные явные имена получают служебный `client_id`, но текст `client_name` остаётся: само наименование не теряется. Запросы и нормативы это правило не использует — они всегда на служебном клиенте.

До ручной перепривязки аналитика по клиентам и подразделениям показывает «Общего клиента» и группу «Без управления». Исторические имена остаются в тексте и в текущих фильтрах.

### 2.6. Замещение норматива при согласовании

Сейчас коммерческий норматив при утверждении гасит предыдущие коммерческие нормативы с тем же `client_name`, артикулом и складом. Excel-нормативы не гасятся.

После появления `client_id` ключ замещения:

1. тот же `client_id`, артикул и склад, `production_request_item_id IS NULL`, строка не удалена;
2. либо прежняя строка привязана к служебному клиенту (`client_code = 9999999999`), и её `client_name` совпадает с именем нового клиента без учёта регистра и краевых пробелов.

Второе правило не даёт удвоить НЗ: новый запрос на клиента, который в истории ещё висит на «Общем клиенте» под тем же именем, гасит старый коммерческий норматив. Excel-партии по-прежнему ничего не гасят.

Замещение по `client_id` в журнал не пишется. Каждое срабатывание второго правила — одна строка в `events`:

| Поле | Значение |
|------|----------|
| event_type | `normative_replaced_by_name` |
| request_id | Запрос, который утверждают |
| processed | `false` |
| payload | `{old_normative_id, new_normative_id, client_name, product_code, warehouse_code}` |

`client_name` в payload — имя, по которому сработало сравнение. `old_normative_id` — погашенная строка, `new_normative_id` — норматив, созданный этим утверждением на том же артикуле и складе. Несколько погашенных строк дают несколько событий.

Тип нужно добавить в `CHECK` таблицы `events` (`ck_events_event_type` в модели и в миграции). Сейчас там только `request_created`, `request_approved`, `request_rejected`, `normative_active`, `normative_expired`, `deficit_detected`, `deficit_resolved`. Длина имени типа — 27 символов, колонка `VARCHAR(50)` его вмещает. Событие пишет приложение в момент утверждения, не триггер. Агент логиста его не обрабатывает: `processed` остаётся `false`, строки нужны, чтобы в первые недели увидеть ложные совпадения имён.

## 3. API

Общий конверт — `SuccessResponse` / `PaginatedResponse`. Ошибки — `APIError` с кодами `VALIDATION_ERROR`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`.

Маршруты `/template`, `/upload`, `/export` регистрируются раньше `/{id}`.

### 3.1. Эндпоинты справочника

| Метод | Эндпоинт | Описание | Права |
|-------|----------|----------|-------|
| GET | `/references/clients` | Список с поиском | любой авторизованный |
| GET | `/references/clients/{id}` | Карточка | любой авторизованный |
| POST | `/references/clients` | Создать | `commercial`, `logistics`, `pp`, `economist` |
| PUT | `/references/clients/{id}` | Обновить | `logistics` |
| DELETE | `/references/clients/{id}` | Soft delete | `logistics` |
| GET | `/references/clients/template` | Шаблон Excel | `logistics` |
| POST | `/references/clients/upload` | Загрузка Excel | `logistics` |
| GET | `/references/clients/export` | Выгрузка Excel | `logistics` |

`guest` справочник читает и не меняет.

### 3.2. Список и поиск

`GET /references/clients`

| Параметр | Описание |
|----------|----------|
| q | Поиск. Строка только из цифр длиной 1…10 — точное совпадение `client_code` **или** точное совпадение ИНН (если 10 или 12 цифр; для более короткой строки — префикс ИНН) **или** `ILIKE` по названию. Иначе — только `ILIKE` по названию |
| department_id | Фильтр подразделения |
| is_active | По умолчанию `true`. Админка может запросить неактивных |
| include_deleted | По умолчанию false |
| page, limit | Как у остальных списков |

Сортировка: `name`, затем `client_code`.

Элемент: `id`, `client_code`, `inn`, `name`, `kpp`, `department_id`, `department_name`, `is_active`, `is_system`.

### 3.3. Создание

Тело: `client_code`, `inn`, `name`, опционально `kpp`. Поле `department_id` зависит от сценария.

Общие правила:

- `client_code` — целое от 1 до 9999999998. Код `9999999999` отклоняется;
- `inn` — 10 или 12 цифр, без контрольной суммы. Значение `0000000000` отклоняется;
- `name` — непустая строка до 500 символов, крайние пробелы снимаются;
- `kpp` — пусто или 9 цифр;
- повтор `client_code` среди неудалённых — `409 CONFLICT`, в теле id существующего клиента;
- совпадение ИНН ошибкой не является.

**Сценарий 1. Форма запроса** (`commercial`, `logistics`, `pp`, `economist`). Поле `department_id` в теле нет. Сервер ставит `users.department_id`. Если у пользователя подразделения нет — `400`, «У пользователя не задано подразделение».

**Сценарий 2. Excel, только `logistics`.** Подразделение берётся из колонки, не из пользователя. См. п. 3.6.

**Создание одной карточки логистом в `/admin/clients`.** То же `POST`. Логист может передать `department_id` (UUID неудалённого подразделения) или `null` («Без управления»). Если поле опущено — наследование, как в сценарии 1. Роли `commercial`, `pp`, `economist` передать `department_id` не могут: `403`.

### 3.4. Обновление

Тело: `name`, `kpp`, `is_active`, `department_id` (`null` допустим и означает «Без управления»).

- `client_code` и ИНН не меняются.
- Служебного клиента обновить нельзя (`400`).
- Неизвестный или удалённый `department_id` — `400`.
- Снимки `client_name` в запросах, нормативах и партиях не переписываются.

### 3.5. Удаление

`deleted_at = now()`, `is_active = false`.

- Служебного клиента удалить нельзя (`400`).
- Запросы, нормативы и партии не трогаются: внешний ключ остаётся, карточка пропадает из автокомплита.
- После soft delete тот же `client_code` можно создать заново.

### 3.6. Excel справочника

Колонки шаблона и загрузки, по порядку:

| Колонка | Обязательность | Описание |
|---------|----------------|----------|
| ID клиента (КССС) | да | Целое 1…9999999998 |
| Наименование | да | Строка |
| ИНН | да | 10 или 12 цифр |
| КПП | нет | 9 цифр |
| ID подразделения | нет | Название подразделения или UUID. Пустая ячейка — `department_id = NULL`, группа «Без управления» |

Подразделение загрузившего на строку не подставляется.

Выгрузка пишет те же колонки плюс «Управление продаж» (название, для чтения) и «Статус». При загрузке название и статус игнорируются. В шаблоне их нет.

Загрузка проверяет каждую строку и не откатывает уже принятые. Ответ как у загрузки остатков: сколько загружено, сколько ошибок, список со номером строки. Не-`.xlsx` и пустой файл — `400`.

Ошибка строки, остальные продолжаются:

- пустой или нечисловой КССС, длина больше 10 знаков, код `9999999999`;
- дубль КССС в файле или среди неудалённых в базе (обновление существующей карточки этой загрузкой не делается);
- ИНН не из 10 или 12 цифр, в том числе `0000000000`;
- КПП задан и это не 9 цифр;
- непустое подразделение, которое не удалось однозначно разобрать (см. ниже).

Непустая ячейка «ID подразделения»:

1. Если значение — UUID, ищется неудалённое подразделение с этим `id`. Найдено — привязать. Нет — ошибка строки «Подразделение с UUID … не найдено». Как название такой UUID не рассматривается.
2. Иначе значение — название. Сравнение точное и без учёта регистра: `lower(btrim(ячейка)) = lower(btrim(departments.name))` среди неудалённых. Одна строка — привязать. Ноль строк — «Подразделение „…“ не найдено». Больше одной — «Найдено несколько подразделений с названием „…“».

В шаблоне под заголовком колонки или комментарием к ней стоит подсказка: «Укажите название подразделения (например, "Коммерческий отдел") или его UUID».

### 3.7. Excel-партии нормативов

`POST /production-requests/upload` переводится на справочник.

В файл добавляется колонка «ID клиента (КССС)». Старая колонка «Клиент» и поле формы «Общий клиент» больше не задают клиента: формальное текстовое поле с формы снимается. Снимок `client_name` сервис пишет сам из найденной карточки.

Правило строки:

| Ячейка КССС | Результат |
|-------------|-----------|
| Пустая | `client_id` служебного клиента (`9999999999`), `client_name = «Общий клиент»` |
| Код есть в справочнике среди неудалённых и активных | `client_id` этой карточки, `client_name` — её наименование |
| Код не найден, клиент удалён или неактивен | ошибка строки, строка не загружается |

`production_requests.client_id` — клиент партии целиком. Если все принятые строки ссылаются на одного клиента, в заголовок пишется он. Если клиенты разные — служебный клиент. Позиция хранит своего клиента в `production_request_items.client_id`. Норматив копирует `client_id` и снимок имени из позиции.

Существующие партии получают `client_id` по п. 2.5.1, тексты `client_name` не трогаются.

### 3.8. Эндпоинты дашборда

Новые блоки читают отдельные методы. `mv_normative_daily` не меняется: текущие графики `/dashboard` группируют НЗ по складу и артикулу без клиента.

| Метод | Эндпоинт | Права |
|-------|----------|-------|
| GET | `/dashboard/nz-by-department` | любой авторизованный |
| GET | `/dashboard/top-clients` | любой авторизованный |

Query: `unit` = `т` (по умолчанию) или `кг`. Пересчёт тот же, что `to_mass` в `dashboard.py`: штуки через `products.weight_kg`, тонна = 1000 кг.

**Объём НЗ** для этих двух методов — сумма количеств активных строк `normatives`, приведённая к выбранной единице.

Активность совпадает с `_active_conditions`: строка не удалена, `expiry_date >= сегодня`, а для Excel-норматива партия не удалена, `status = active` и `valid_from <= сегодня`.

В сумму не входят коэффициент категории и коэффициент удалённости. Это не потребность и не дефицит.

Считать нужно по строкам нормативов, без схлопывания родственных артикулов. Схлопывание групп (`parent_code` / `children_code`) остаётся только на дашборде логиста, в расчёте дефицита. В аналитические блоки его переносить нельзя: там объём главного артикула уже включает родственников, а клиенты строки смешаны.

`GET /dashboard/nz-by-department` группирует по `clients.department_id`, внутри подразделения — по складу. Клиенты с пустым подразделением, включая служебного, — группа «Без управления». Ответ: `department_id`, `department_name`, `warehouses[]` (`warehouse_code`, `warehouse_name`, `nz_quantity`), `unit`. Общие фильтры `department_id` и `warehouse_code`. Сортировка подразделений по сумме объёма по убыванию.

`GET /dashboard/top-clients?limit=10` группирует по `clients.id`. Ответ: `client_id`, `client_code`, `client_name` (актуальное имя справочника), `inn`, `department_name`, `nz_quantity`, `is_other`, `unit`. Нулевые объёмы в топ не попадают. Общие фильтры `department_id` и `warehouse_code`. После топа, если остался объём, идёт «Остальные» (`is_other = true`) и всегда замыкает список.

## 4. Frontend

### 4.1. Создание запроса

Страница `/requests/create`. Сейчас поле «Клиент» — свободный `Input`.

Станет автокомплитом:

- поиск `GET /references/clients?q=&is_active=true`;
- в списке: код КССС, наименование, ИНН;
- выбранное значение — `client_id`;
- кнопка «Создать клиента» рядом с полем.

Модалка (сценарий 1):

- ID клиента (КССС), обязательно, целое до 10 знаков, не `9999999999`;
- ИНН, обязательно, 10 или 12 цифр;
- наименование, обязательно;
- КПП, необязательно, 9 цифр;
- подразделение на форме не выбирается; если оно есть у пользователя, показывается текстом («будет привязан к …»);
- если подразделения нет — создание недоступно;
- после `201` новый клиент выбран в поле запроса.

Черновик (`PUT /requests/{id}`) принимает `client_id` и обновляет снимок `client_name`. Менять клиента можно только в `draft`.

Карточка запроса, «Мои запросы», согласование и модалка согласования показывают имя: `clients.name` по `client_id`, если связь есть, иначе снимок `client_name`.

### 4.2. Администрирование

«Администрирование» — подменю, не вкладки: Пользователи, Подразделения, Параметры. Новый пункт **«Клиенты»**, маршрут `/admin/clients`, только `logistics`.

Таблица: КССС, ИНН, Наименование, КПП, Управление продаж, Статус. Служебная строка без кнопок правки и удаления.

Поиск по коду КССС, ИНН и названию.

Кнопки: «Создать», «Выгрузить в Excel», «Загрузить из Excel», правка, удаление (Popconfirm).

Модалка создания для логиста: те же реквизиты, плюс подразделение — select из `GET /admin/departments` с пустым значением «Без управления».

Правка (сценарий 3): наименование, КПП, активность, подразделение, в том числе сброс в «Без управления». КССС и ИНН только для чтения.

Загрузка показывает отчёт «загружено / ошибок».

### 4.3. Дашборд

Новые блоки на аналитическом `/dashboard` (пункт меню «Дашборд»). На `/logistics/dashboard` их нет.

Дашборд логиста не меняется. Родственные артикулы по-прежнему схлопываются в главный для норматива, потребности и дефицита. Клиенты в колонке по-прежнему перечисляются через запятую и в агрегат не схлопываются.

Блоки `/dashboard`:

1. **НЗ в разрезе управлений продаж** — горизонтальные бары по `GET /dashboard/nz-by-department`, стек складов цветами `warehouseTrendColors`. Подписи подразделений не обрезаются. Группа «Без управления» обязательна.
2. **Топ-10 клиентов по объёму НЗ** — горизонтальная столбчатая диаграмма по `GET /dashboard/top-clients`, плюс серый бар «Остальные» в конце.

Единицы — те же тонны и килограммы, что уже переключаются на `/dashboard`. Штуки для этих блоков не предлагаются.

Пустое состояние: «Нет активных нормативов».

### 4.4. Партии нормативов

На вкладке загрузки партий:

- колонка файла «Клиент» заменяется на «ID клиента (КССС)»;
- текстовое поле «Общий клиент» убирается;
- пустая ячейка в подсказке к файлу объясняется как «Общий клиент»;
- в таблице партий и строк показывается наименование из справочника (через `client_id`), рядом можно оставить снимок, если имя в справочнике уже другое.

### 4.5. Что не меняется

- Фильтр клиента на `/logistics/one-time` и `GET /logistics/one-time/clients` (уникальные строки `requests.client_name`).
- Текстовые фильтры клиента на «Мои запросы», согласованиях и «Нормативах».
- Выгрузка разнарядок B2B.
- Расчёт дефицита, покрытия, тренда, исключений и календаря.

## 5. Влияние на текущую логику

### 5.1. Не ломается

| Место | Почему |
|-------|--------|
| Дефицит на `/logistics/dashboard` | Склад и группа артикулов, как сейчас. Клиенты в колонке склеены через запятую. Формула потребности и дефицита не меняется |
| Покрытие, тренд, исключения, календарь | Склад и артикул. `mv_normative_daily` не трогаем |
| Существующие запросы и нормативы | `client_id` служебного клиента, текст `client_name` на месте |
| Существующие партии | `client_id` по точному имени, если в справочнике ровно одна такая карточка; иначе служебный клиент. Текст `client_name` на месте |

| Фильтр разовых | `ILIKE` по `requests.client_name` |
| Выгрузки с колонкой «Клиент» | Пишут снимок `client_name`: Excel дефицита, Excel разового, Excel нормативов на дату |

Колонка «Подразделение» в выгрузке нормативов — подразделение инициатора или автора партии, не подразделение клиента. Смысл не меняется.

| Место | Изменение |
|-------|-----------|
| `requests` | Обязательный `client_id`. Черновик принимает `client_id`. `client_name` сервис заполняет из справочника |
| `normatives` | Обязательный `client_id`. При утверждении копируются оба поля. Замещение — п. 2.6 |

## 6. Критерии приёмки

- [ ] Таблица `clients` создана, у `client_code` уникальность среди неудалённых и предел в 10 знаков.
- [ ] Служебный клиент: `client_code = 9999999999`, `inn = 0000000000`, имя «Общий клиент», `is_system = true`, подразделение пустое.
- [ ] Все существующие `requests` и `normatives` ссылаются на служебного клиента, тексты `client_name` не изменены.
- [ ] Партия с пустым `client_name` ссылается на служебного клиента. Партия с именем, которое точно совпадает с одной карточкой справочника, ссылается на неё. Имя без карточки или с несколькими карточками — служебный клиент. Тексты не изменены.
- [ ] CRUD клиентов работает с правами из п. 3.1.
- [ ] Поиск находит по коду КССС, по ИНН и по части названия.
- [ ] Создание из формы запроса наследует подразделение пользователя и само выбирает новую карточку в запросе.
- [ ] Пользователь без подразделения получает ошибку.
- [ ] Дубль КССС возвращает 409. Повтор ИНН сам по себе не ошибка.
- [ ] Служебного клиента нельзя изменить и удалить. Код `9999999999` нельзя занять.
- [ ] Excel клиентов: колонки КССС, Наименование, ИНН, КПП, ID подразделения. Пустая ячейка подразделения даёт «Без управления». Название ищется точно, без учёта регистра; ноль или несколько совпадений — ошибка строки. UUID по-прежнему принимается. В шаблоне есть подсказка про название и UUID.
- [ ] Логист в `/admin/clients` меняет подразделение, в том числе сбрасывает его.
- [ ] Excel-партия: колонка «ID клиента (КССС)» заполняет `client_id`. Неизвестный код — ошибка строки. Пустая ячейка — служебный клиент.
- [ ] `/dashboard` показывает НЗ по подразделениям и топ-10 клиентов в тоннах и килограммах, без коэффициентов и без схлопывания родственных артикулов.
- [ ] Дефицит на дашборде логиста по-прежнему схлопывает родственные артикулы и перечисляет клиентов через запятую.
- [ ] Новый коммерческий запрос гасит старый коммерческий норматив того же артикула и склада, если совпал `client_id` или (для строки на служебном клиенте) имя.
- [ ] Замещение по имени пишет `events` с типом `normative_replaced_by_name` и payload из п. 2.6. Замещение по `client_id` событие не пишет. Тип добавлен в `CHECK` таблицы `events`.
- [ ] Фильтр клиента в разовых перемещениях работает по тексту.
- [ ] Выгрузка B2B не меняется.
- [ ] Тесты бэкенда и фронтенда проходят.

## 7. Риски и митигация

| Риск | Митигация |
|------|-----------|
| Обязательный `client_id` ломает старые строки | Миграция ставит служебного клиента, текст имени не стирает |
| Топ-10 и разрез по управлениям сразу после миграции показывают одного «Общего клиента» | Так задумано. Группа на графике называется «Без управления» |
| Новый запрос не гасит старый норматив, НЗ удваивается | Замещение и по `client_id`, и по имени для строк на служебном клиенте (п. 2.6) |
| Ложное гашение по похожему имени | Событие `normative_replaced_by_name` с id старого и нового норматива. Замещение только по `client_id` в журнал не пишется |
| Явное имя партии потеряется при миграции | Пустое имя → служебный клиент. Точное совпадение с одной карточкой → она. Иначе служебный клиент, текст `client_name` не стирается. На старте миграции в справочнике только служебная карточка, поэтому прочие имена сопоставятся, только если карточки загружены до UPDATE |
| Два клиента с одним ИНН | Нормально: уникален КССС, не ИНН |
| Ошибки Excel | Построчная валидация и отчёт. Успешные строки сохраняются. Неизвестный КССС в партии не создаёт клиента сам |
| Замедление дашборда | Индекс `normatives.client_id`. Новые агрегаты отдельно от `mv_normative_daily` и от расчёта дефицита |
| Логист из формы запроса заводит клиента в подразделение «Логистика» | На форме запроса наследование сохраняется. В Excel и в правке логист ставит подразделение явно, пустое значение законно |
| Подразделения в системе функциональные, а не «управления продаж» | Группировка идёт по `departments`. Новый тип подразделения не вводится |
| Схлопнуть родственные артикулы ещё и в топ-10 | Аналитика суммирует строки нормативов. Схлопывание остаётся только в дефиците логиста |
| Переименование расходится со снимком в старых запросах | История хранит снимок. Дашборд показывает актуальное имя |
| Удаление клиента, на которого есть ссылки | Soft delete, `ON DELETE RESTRICT`. Экраны показывают снимок имени |
| Колоночный UNIQUE не даст повторить КССС после удаления | В миграции только частичный уникальный индекс `WHERE deleted_at IS NULL` |

## 8. Закрытые вопросы

| Вопрос | Решение |
|--------|---------|
| Подразделение при создании | Форма запроса наследует `users.department_id`. Excel принимает точное название или UUID, пустая ячейка = `NULL`. В `/admin/clients` логист меняет подразделение |
| Уникальность | `client_code` среди неудалённых. ИНН и пара ИНН+КПП не уникальны |
| Где графики | Только аналитический `/dashboard`. Дашборд логиста без новых блоков |
| Партии нормативов | Колонка КССС. Пусто — служебный клиент. Неизвестный код — ошибка строки. Старые партии: пустое имя или нет единственного совпадения в справочнике — служебный клиент; точное имя одной карточки — эта карточка |
| История имён | Отдельные карточки из старых `client_name` не создаются |
| Контрольная сумма ИНН | Не проверяется. Только 10 или 12 цифр. КПП — 9 цифр, если задан |
| Объём НЗ | Сумма активных нормативов в т/кг, без коэффициентов категории и удалённости, по строкам, без схлопывания артикулов |

Открытых вопросов, блокирующих реализацию, нет.

## Приложение A. Где сейчас используется `client_name`

Таблица `clients` отсутствует. Поле — свободный текст. Это снимок кода до фичи.

### Хранение

| Таблица | Поле | Ограничение |
|---------|------|-------------|
| `requests` | `client_name` | `NOT NULL`, индекс `idx_requests_client_name` |
| `normatives` | `client_name` | `NOT NULL`. Копируется из запроса при утверждении или из строки Excel-партии |
| `production_requests` | `client_name` | nullable, общий клиент партии |
| `production_request_items` | `client_name` | `NOT NULL`. Итог: клиент строки, иначе общий клиент партии, иначе пустая строка |

### Запись

- `POST /requests`, `PUT /requests/{id}` — тело `client_name`. `department_id` запроса копируется из `users.department_id` и к клиенту не относится.
- Утверждение ПП/экономиста — `normatives.client_name = requests.client_name`. Предыдущие коммерческие нормативы того же имени, артикула и склада мягко удаляются.
- `POST /production-requests/upload` — необязательный form-параметр `client_name` и колонка «Клиент» в Excel.

### Чтение и фильтры

- `GET /requests`, согласования, нормативы, разовые — `ILIKE` по `client_name`.
- `GET /logistics/one-time/clients` — уникальные имена разовых запросов, не справочник.

### Экраны

- `/requests/create` — свободный ввод.
- Карточка, списки, согласования — показ `client_name`.
- `/logistics/dashboard` — колонка «Клиент»: имена склеены через запятую. Агрегации по клиенту нет. Родственные артикулы схлопнуты в главный.
- Вкладка партий — текстовое поле «Общий клиент».

### Выгрузки

| Выгрузка | Колонка «Клиент» |
|----------|------------------|
| `GET /logistics/normative/export` | Да, склейка имён |
| `GET /logistics/one-time/{id}/export` | Да, `requests.client_name` |
| `GET /normatives/export` | Да. Рядом подразделение инициатора, не клиента |
| `POST /logistics/normative/export-b2b` | Нет |

### Дашборды

- `/dashboard`: склад и артикул. Клиента в группировках нет.
- `/logistics/dashboard`: дефицит по складам и группам артикулов. Клиент — подпись строки.

### Пользователи и подразделения

`users.department_id` → `departments.id`, поле необязательное. Рядом денормализованное название `users.department`. У гостя в сидах подразделения нет. У логиста в сидах подразделение «Логистика».

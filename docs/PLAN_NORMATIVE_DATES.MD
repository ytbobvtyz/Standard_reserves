# План. Даты действия коммерческого норматива

Статус: согласован 02.11.2026, реализован.

Текущие `DATA_MODEL.MD`, `API_SPECIFICATION.MD` и `FRONTEND_SPEC.MD` описывают прежнее поведение флага `auto_complete_previous` (галочка в окне расчёта, завершение всех коммерческих нормативов клиента). При реализации эти три документа заменить на правила ниже.

## Инвариант

У запроса один срок. Он двигается целиком, вместе со всеми его нормативами. Отдельный срок у строки, разрезание запроса и удаление части позиций запроса не делаем.

Новый коммерческий норматив всегда начинается на следующий день после даты утверждения экономистом. В день утверждения логист берёт в работу ещё прежний объём.

`expiry_date` включительная: норматив с этим сроком действует в день окончания и выпадает из активных выборок на следующий день. Фильтр `expiry_date >= CURRENT_DATE` не менять.

## Коммерсант. Расчёт оптимального запаса

Кнопка «Рассчитать оптимальный запас» по-прежнему только для нормативного запроса, активна сразу, без клиента просит его выбрать. Расчёт смотрит все отгрузки клиента.

Окно остаётся обзором:

- рассчитанные позиции и пропущенные с причиной;
- действующие коммерческие нормативы клиента со ссылкой на запрос, ссылка открывается в новой вкладке;
- предупреждение, если количество уже введённых строк будет перезаписано.

Галочки завершения в этом окне нет. «Применить» только заполняет строки запроса. После этого коммерсант может править количество, удалять и добавлять позиции. «Отмена» форму не меняет. Смена клиента по-прежнему сбрасывает несохранённый выбор завершения.

## Коммерсант. Отправка

«Сохранить черновик» не записывает решение о завершении старых запросов.

Решение принимается в момент отправки и не зависит от того, откуда взялись строки. Один и тот же шаг на форме создания по кнопке «Отправить» и на карточке черновика по кнопке «Отправить на согласование».

Система берёт позиции, которые реально уходят в запрос, и ищет действующие коммерческие нормативы этого клиента с теми же парами продукт + склад. Действующий: `deleted_at IS NULL`, `expiry_date >= сегодня`, не строка Excel-партии. Одинаковые запросы показываются один раз.

Если таких запросов нет, дополнительного вопроса нет, флаг остаётся `false`.

Если есть, коммерсант видит список: номер запроса, дата, ссылка на карточку в новой вкладке. Одна галочка на весь список, по умолчанию включена. Текст под галочкой один: при включении — про завершение запросов в день утверждения, при снятии — про увеличение без отмены прежнего норматива.

- Галочка включена. Эти запросы завершатся в день утверждения экономистом. Завершится каждый запрос целиком, включая позиции, которых нет в новом. До утверждения они действуют как сейчас. Новый норматив начнётся на следующий день.
- Галочка снята. Это увеличение по уже существующей позиции. Прежние запросы и все их позиции остаются до своего срока. Количество нового запроса прибавится к действующему. Новый норматив тоже начнётся на следующий день, поэтому в день утверждения объём ещё прежний, со следующего дня объёмы складываются.

Нормативы Excel в список не входят.

## Что видят ПП и экономист

Блок на карточке запроса и в окне согласования. Это пометка, а не второй переключатель: ПП и экономист не меняют выбор коммерсанта. Согласование или отказ относятся ко всему запросу.

- `auto_complete_previous = true`: «Коммерсант завершает действующие запросы в день утверждения» и ссылки на эти запросы, каждая в новой вкладке.
- `auto_complete_previous = false` и по позициям запроса есть действующие коммерческие нормативы: «Увеличение по действующей позиции, прежний норматив сохраняется. Количество прибавится к текущему» и те же ссылки.

Список для пометки считается по текущим позициям запроса тем же правилом, что и при отправке.

## Утверждение экономистом

Пока экономист не утвердил, нормативы не меняются. Отказ их не меняет. Согласование ПП даты не двигает.

Для каждой новой коммерческой строки норматива:

- `valid_from` = день утверждения + 1;
- `expiry_date` = срок запроса.

Если коммерсант подтвердил завершение, у каждого найденного запроса `requests.expiry_date` и `expiry_date` всех его неудалённых нормативов становятся днём утверждения. В этот день старый запрос ещё действует. Со следующего дня действует новый. Другие нормативы клиента, не попавшие в найденные запросы, не меняются. Excel не меняется.

Если коммерсант не подтвердил завершение, старые запросы не меняются: ни срок, ни строки. Новая строка живёт рядом со старой. Панель логиста по-прежнему суммирует количество нескольких действующих нормативов одной пары продукт + склад.

Мягкое удаление прежней строки той же пары продукт + склад при каждом утверждении отключается. Иначе отказ от завершения погасит позицию, хотя коммерсант просил её оставить. Замена по совпадению имени системного клиента этим же правилом больше не снимает строку сама по себе.

## Данные

Колонка `requests.auto_complete_previous` остаётся. Смысл другой: коммерсант при отправке согласился завершить найденные запросы в день утверждения экономистом. В запрос попадает только в момент отправки. Черновик и «Применить» в расчёте её не выставляют.

У коммерческого норматива появляется `normatives.valid_from`. Для уже существующих строк заполнить календарной датой `created_at`, чтобы история не сдвинулась. Для строк, созданных утверждением после этой доработки, писать день утверждения + 1.

Строка Excel по-прежнему начинается с `production_requests.valid_from`. Собственный `valid_from` коммерческой строки на партию Excel не подменяет её условия `status = active` и отсутствие удаления партии.

Активная выборка коммерческой строки: не удалена, `valid_from <= сегодня`, `expiry_date >= сегодня`. Это же условие в сводке дашборда, панели логиста, `GET /normatives`, аналитике и в списке действующих нормативов расчёта оптимального запаса.

## Отправка в API

`POST /requests` с немедленной отправкой принимает флаг вместе с запросом.

`POST /requests/{id}/submit` принимает тот же флаг в теле. Карточка черновика записывает выбор этим вызовом. Сохранение черновика флаг не меняет.
